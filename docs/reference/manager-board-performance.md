# 经理看板刷新与大看板基准

2026-11-03，基线 `167020f1`（0.29.0）。测试只使用临时 SQLite、假引擎、
隔离浏览器、临时 SSH 密钥和回环 sshd，没有读取用户的设备、会话或状态目录。

## 答复后仍在待定

**事实**

- 桌面 `Decisions` 与手机 `Issue` 都通过核心提交答复。原核心收到成功结果后只
  `invalidate`，重新调用 `board/read`；没有把 `accepted` 中已保存的决策写入看板投影。
- 设备 `boardChanged` 也触发整板重读，不直接携带对象增量。核心会丢弃读取过程中
  又被通知标为失效的快照，再补读一次。因此成功答复与界面状态改变之间还隔着整板读取。
- 真实 WebSocket 夹具还确认：设备通知先触发读取，成功回包又 `invalidate`，
  同一笔答复会连读两次整板；旧实现中第一次结果被主动丢弃。
- 无故障的手机模拟核心专项检查通过。正式 `createManagers` 加故障夹具则在两端复现：
  设备不给通知，提交后的整板读取一直挂起，提交已成功但桌面卡片仍在待定、手机仍可答复。
  这证明了客户端对重读的依赖，不等同于已经复现用户真实设备当时的全部条件。
- 0.28.0、0.28.1 源码的 `answersSubmit` 已调用 `changed`，后者已发 `boardChanged`。
  新客户端的现有旧设备分支也主动 `invalidate`；单纯缺少通知不足以解释永久不刷新。
- 桌面切换决策分栏只改变本地筛选，不会独立请求看板；重挂经理看板则可能重新订阅。

**推测**

用户的重读可能被下面的大看板成本、工作线读取、网络延迟或读失败拖住。
切页签时消失可能恰好赶上重读完成。真实旧设备版本及当时请求时序未取得，不能定论。

**修复**

- 成功回包先把 `accepted` 的权威状态同步进两端共用看板，并更新待定计数，再后台补读历史与动态。
  没有提交前的猜测性隐藏；失败不改状态，原有界面负责保留草稿、显示错误。
- 只接受更高 revision；成功部分立即更新，失败部分保留；提交前在途旧快照仍按失效规则丢弃。
- 保持 I-67：桌面停在待定，接续下一项；手机留在控制台并显示已答状态。
  手机控制台包含已答卡片，成功后退出的是待答状态，不是从“全部决策”里删除卡片。
- 已由通知观察器加载、持续订阅的看板直接复用；新增界面读者不再让首次读取作废或重复读取。
- 纯答复全部成功时复用通知已发起的读取，以成功回包 revision 为下限核验。
  读回的是提交前旧版本才补读；回包前已经有更高版本的完整看板则不再重读。
  部分失败、夹带追问或交付仍按原失效规则完整对账。

成功之后的更新范围：

| 数据 | 更新来源 |
|---|---|
| 决策状态、答案、revision、修改时间 | 成功回包立即应用 |
| 待定/已答分组、待定计数、概况中的决策数 | 由更新后的投影立即重算 |
| 对应帖子的 revision、修改时间 | 成功回包立即应用 |
| 完整变更历史、帖子旧版本、动态时间线 | 后台整板对账 |
| 事项、工作线事实、讨论或其它并发改变 | 后台对账/后续设备通知；不能从答案猜测 |

“立即”指收到服务器成功回包后发布；仍需通道的一帧合并与 React 提交，不是点击前先隐藏。

## 加载链路与规模

现有链路：经理 `list` → 所有工作线 `thread/read` → 经理摘要 → `board/read` →
再次读取工作线 → 全部对象、历史、帖子版本、关联及动态 → JSON → 核心投影 → 界面。

看板没有分页。`changes` 保存整份 before/after，`posts.versions` 又带旧正文，
`activities` 从历史生成。通知只做失效重读，不是对象增量；开启桌面通知的经理会常驻观察看板。
首屏待定列表只需当前待定决策及其帖子、状态和计数；事项、工作线、旧决策、全部审计正文
以及全部历史动态都不必随首屏传输。重开理由等少量历史派生字段需要保留在摘要中。
本例待定分栏装入 20 张卡；1440×1000 的桌面窗口首屏只露出第一张卡的部分正文，
却已经收到 40 条已答决策、100 条事项、50 条工作线和全部 2400 条审计记录。

基准数据：60 条决策（20 待定、40 已答）、100 条事项，每对象 15 次变更，共 2400 条；
50 条工作线，每条假 `thread/read` 等待 20ms、并行完成；背景约 400 个中文字符。
序列化看板 **10,807,850 bytes**，前后字节数相同。

主要载荷：审计历史 8.57 MB、帖子含旧版本 1.36 MB、动态 0.51 MB、
决策 0.12 MB、事项 0.15 MB、关联 0.08 MB、工作线 0.016 MB。
数据量取决于正文长度；此数值不是所有 60/100 看板的固定大小。

## 分段测量

Apple M3 Pro、Node 24.21.0，设备与核心 CPU 阶段各 5 次，表中为中位数。工作线是可控假延迟，
不是用户的真实 harness 延迟。所有数字单位为毫秒。

| 阶段 | 改前 | 改后 | 口径 |
|---|---:|---:|---|
| 经理列表 RPC | 5557.2 | 101.2 | 含工作线刷新和摘要构造，不含网络 |
| 看板读取 RPC | 8354.2 | 101.1 | 含身份校验、工作线刷新、看板构造，不含网络 |
| 单独构造看板 | 2757.1 | 92.1 | SQLite 读取、JSON 解析与设备投影，已含在上面 RPC 内 |
| 单独读取一次全部历史 | 43.8 | 88.7 | 已含在构造中；分配/GC 波动，未声称此查询本身加速 |
| 序列化完整看板 | 14.8 | 18.6 | 同样的 10.8 MB，未改变载荷 |
| 客户端 JSON 解析 | 15.0 | 25.6 | 同样的 10.8 MB |
| 核心看板投影 | 4.5 | 5.4 | 不含 UI，不改变算法 |
| 桌面看板订阅至首帧 | 519.2 | 490.0 | 3 次中位数，正式 App/Vite/隔离 Chrome，见下文 |

桌面首帧仅对比历史渲染前后，共用修复后的核心与同一份数据；MutationObserver
观察第一张决策卡，随后等两次 requestAnimationFrame，不把 CDP 轮询时间计入。
改前样本 519.2/529.9/518.3；改后 502.3/482.3/490.0。
收起历史仍挂载的 article 数从 **300 → 0**，展开仍能看到旧版本正文。
手机正式网页预览改后一次约 **200.6ms**；未修改手机渲染，也未作手机前后性能结论。

同一 JSON 的传输另测 7 次，使用已经连接的 WebSocket，包含一次小请求往返和响应传送：

| 传输方式 | 中位数 | 建连 |
|---|---:|---:|
| 本机回环 WebSocket | 26.8ms | 7.6ms |
| 真实 OpenSSH 转发到回环 WebSocket | 53.0ms | SSH 54.7ms，WebSocket 1.4ms |

传输前后没有改变，故复用同一载荷测量。SSH 使用临时用户态 sshd、独立密钥和
known_hosts，只转发端口、不启动登录 shell；它证明 SSH 路径开销，**不代表公网 RTT 和带宽**。

设备列表加看板读取约 **13.91s → 0.20s**。把各独立阶段相加，桌面已有连接时
本机约 **14.49s → 0.77s**，回环 SSH 约 **14.52s → 0.80s**。
这是分段估算，不是整台 Electron 从进程启动到可见窗口的端到端成绩；
不含应用载入、设备发现、真实 SSH 登录、真实工作线读取延迟及其它经理的竞争。
阶段有重叠时不能简单相加，“单独构造”和“单独读取历史”不得再次加入 RPC 总数。

## 答复后其它数据为什么也慢

补测使用同一份大看板，真实设备管理模块入库、发通知，浏览器正式 App 通过正式核心、
通道和副本更新，完整看板入副本后等待两次 requestAnimationFrame。
前后共用当前界面渲染，分别加载基线与修复后的设备/核心代码；同源 Vite 代理保留正式 CSP。
本机与真实回环 SSH 各测一次。计时从实际发送成功那次答复开始，不含故意注入的失败重试。

| 链路 / 阶段 | 改前 | 改后 |
|---|---:|---:|
| 本机：提交到成功回包 | 10881.3ms | 66.7ms |
| 本机：提交到答案/计数首帧 | 27370.7ms | 190.5ms |
| 本机：提交到完整看板落帧 | **27370.7ms** | **352.6ms** |
| 本机：成功回包后仍等待完整刷新 | 16489.4ms | 285.9ms |
| SSH：提交到成功回包 | 10889.5ms | 60.5ms |
| SSH：提交到答案/计数首帧 | 29083.0ms | 185.8ms |
| SSH：提交到完整看板落帧 | **29083.0ms** | **368.6ms** |
| SSH：成功回包后仍等待完整刷新 | 18193.5ms | 308.1ms |
| 每次成功答复之后的整板读取次数 | **2** | **1** |

改前是“提交本身重复构板 + 通知重读 + 成功回包再失效补读”；三段串起来，
所以不只是待定卡片，已答分组、计数、帖子时间和概况都一起晚到。
改后成功回包先更新能够确认的字段，后台的一次快照补齐审计/动态和其余数据。
这次测试关闭假经理的模型回合启动，不包含真实模型随后写出的新进度；也不是公网带宽测量。
SSH 的回包略快于本机属于单次 CPU/调度波动，不能解释为 SSH 本身加速。

“不重读整板”在这个链路中已省去重复的第二次；完全取消剩余一次须实现下面的增量协议。

## 加载修复

原 `posts.list` 为每张帖子重新 `store.changes`，每次读取、解析全经理的审计历史；
`manager()` 已构造一次看板，又重做一次帖子列表；`board/read` 的身份校验也先构造一次经理摘要。
这是确定的重复计算，复杂度随帖子数乘历史体量增长。

- 每份看板只读取历史一次，按对象分组供帖子投影使用。
- 经理摘要复用已构造的帖子；路由只查经理是否存在，不再构造摘要来验证身份。
- 相同基准 5 轮（每轮列表、看板 RPC、单独构板）的全历史读取次数 **1820 → 15**。
  未改表、索引、磁盘记录、协议响应形状及内容。
- 桌面收起的历史正文在展开时才生成 Markdown/DOM。数据仍在完整看板里，不能称为按需网络读取。

## 后续协议方案（未实施，需经理决定）

当前修复足以去掉本例主要 CPU 瓶颈，但载荷仍随历史无限增长；低带宽远程设备仍可能慢。
列表与看板还各刷新全部工作线，一条慢线也会拖住整板。这些是明确的剩余设计成本。

建议单独设计一个可协商的摘要扩展，不修改旧 `board/read`：

1. 新增经理摘要/看板概览读取方法：计数、局势、当前对象摘要、首批待处理议题、
   少量最新动态、工作线最近快照。摘要显式提供重开原因和上次关闭记录；不用全审计来算。
2. 新增按种类/状态列对象的游标分页方法；已关闭、已答、完成事项按需加载。
   单条详情返回背景、选项、依据、讨论；版本历史另按对象和 seq 游标读取。
3. 工作线事实刷新独立于首屏：明确快照新鲜度，收到新的事实再更新工作线。
   原 full-board 方法保持原语义；新摘要方法不能把未知状态冒充“空闲”。
4. 新扩展声明后才发新对象/计数变更；仍按接收的连接能力投递。
   采用单调 boardRevision、断线重读和分页快照游标，处理并发修改、重开与漏推。
   不向旧客户端发送新通知，不缩减旧返回字段。
5. 先复用现有表做查询；是否增加 object_id 列或 JSON 表达式索引，应在历史分页
   查询计划与更大数据量测试后另行批准，不把存储迁移塞入本修复。

若要让答复后完全不重读整板，应在新扩展中新增提交方法，返回原有 accepted/rejected
及同次事务产生的 manager/decision/post 补丁、权威审计记录和动态、boardRevision。
新通知沿相同修订序列发送补丁，客户端去重，漏号或重连再按游标补取。
现有成功回包没有审计记录 ID、why/fields 或完整动态，也无法涵盖经理同时改的其它对象，
所以不能仅凭客户端拼一条时间线就删掉对账。这个协议/修订序列设计本轮未实施。

## 复跑与验收

使用 Node 24，先安装依赖并构建 device/core；手机预览还需 `npm run web:build --prefix apps/mobile`。

```sh
npm run build --prefix packages/device
npm run build --prefix packages/core
node scripts/bench-manager-board.mjs /tmp/manager-board.json
node scripts/bench-manager-board-transport.mjs /tmp/manager-board.json
node scripts/bench-manager-board-refresh.mjs /tmp/manager-board.json 167020f1 --ui
npm run dev --prefix packages/ui -- --host 127.0.0.1 --port 5197
node scripts/check-manager-board-ui.mjs /tmp/manager-board.json
node scripts/check-manager-board-ui.mjs /tmp/manager-board.json --mobile
```

界面脚本使用 Chrome for Testing 的隔离配置目录，可用 `LITCH_CHROME_BINARY` 指定。
`--mobile` 临时创建 `.web.ts` 替身，再起独立端口的 Metro，结束后都清理；不修改原生入口。
截图只写入 `/tmp`。`--expect-stale` 仅用于旧核心对照：预期成功答复后卡片仍待定。
刷新基准只读指定 git 提交，经 esbuild 构建临时基线模块，不覆盖工作树或 dist；
`--ui` 自己启动同源 Vite 代理，保留正式 CSP，用正式 App/通道/副本测到完整看板落帧。
它只禁止假经理开始模型回合；决策入库、事件排队、通知、重读均走生产实现。

专项证据：核心经理相关 54 项、设备 manager/manager-posts/manager-board-read 18 项、
桌面提交焦点 5 项；两端正式界面的无通知/慢重读/失败重试；核心部分失败、旧在途读取、
更新 revision 优先、旧设备答复路径、通知读取复用；桌面展开历史；手机常规经理工作台检查。

未验：用户真实旧设备版本与现场网络请求时序；真实公网 SSH；Android/iOS 原生窗口；
真实 Electron 全进程冷启动。没有触发全量 CI、推送或发布。
